# go-solid-refactoring

Учебный проект: рефакторинг системы управления заказами по принципам SOLID. Исходная реализация сохраняла заказ в SQLite и одновременно отправляла email-уведомление внутри одного метода, что жёстко связывало бизнес-логику с конкретной БД и конкретным каналом уведомлений. После рефакторинга `OrderService` зависит только от интерфейсов `RepositoryWriter` и `Notifier` и не знает ни о SQLite, ни о способе доставки уведомления.

## Стек

- Go 1.26
- `github.com/mattn/go-sqlite3` — драйвер SQLite (требует CGO)
- Только стандартная библиотека в остальном: `database/sql`, `errors`, `fmt`, `log`, `testing`

## Что показывает

- Рефакторинг по всем пяти принципам SOLID с конкретными примерами в коде.
- Инверсию зависимостей: `OrderService` получает `RepositoryWriter` и `Notifier` через конструктор.
- Подстановку разных реализаций `Notifier` (email и SMS) в один и тот же `OrderService` без правок в его коде.
- Разделение интерфейсов для БД на `RepositoryWriter` и `RepositoryInitializer`.
- Обёртывание ошибок через `%w` для сохранения контекста и проверки в тестах через `errors.Is`.
- Тесты на моках (`MockWriter`, `MockNotifier`) — три сценария без реальной БД и без реальной отправки.

## Как устранены жёсткие связи

| Принцип | Как реализован в решении |
|---|---|
| S — Single Responsibility | `SQLiteRepo` отвечает только за работу с БД, `EmailSender`/`SMSSender` — только за отправку уведомления, `OrderService` — только за бизнес-логику создания заказа |
| O — Open/Closed | `OrderService` не меняется при добавлении новых БД или каналов уведомлений — достаточно реализовать существующий интерфейс новой структурой (`SMSSender` добавлен без единой правки в `OrderService`) |
| L — Liskov Substitution | `EmailSender` и `SMSSender` реализуют единый контракт `Notifier.Send(customer, message string) error` и взаимозаменяемы — `OrderService` работает с любым из них без проверок конкретного типа |
| I — Interface Segregation | Инициализация БД (`RepositoryInitializer.Init()`) вынесена отдельно от записи (`RepositoryWriter.SaveOrder()`) — клиенты, которым инициализация не нужна (например, тестовый мок), не обязаны её реализовывать |
| D — Dependency Inversion | `OrderService` получает `RepositoryWriter` и `Notifier` через конструктор `NewOrderService(repo, notifier)`, а не создаёт конкретные реализации внутри себя |

## Ключевые решения

### Порядок операций в CreateOrder

Сначала `SaveOrder`, затем `Notifier.Send`. Это осознанный выбор:

- если `SaveOrder` упадёт — уведомление не отправляется, клиент не получит ложное подтверждение;
- если `Send` упадёт после успешного `SaveOrder` — заказ остаётся в БД, клиент без уведомления. Это приемлемо: уведомление можно переотправить, а заказ не потерян;
- обратный порядок был бы хуже: клиент мог бы получить подтверждение заказа, которого нет в БД.

### Обёртывание ошибок через %w

В `CreateOrder` ошибки оборачиваются с контекстом:

```go
if err := s.repo.SaveOrder(order); err != nil {
    return fmt.Errorf("сохранение заказа: %w", err)
}
if err := s.notifier.Send(customer, message); err != nil {
    return fmt.Errorf("отправка уведомления: %w", err)
}
```

Это даёт две вещи: понятный контекст в тексте ошибки и возможность проверить исходную ошибку через `errors.Is` в тестах.

### Разделение RepositoryWriter и RepositoryInitializer

Не все клиенты `RepositoryWriter` нуждаются в инициализации схемы. `MockWriter` в тестах реализует только `SaveOrder` — и это корректно, потому что `Init()` ему не нужен. Классический пример Interface Segregation.

### Один OrderService с двумя Notifier

В `main` продемонстрировано: тот же `OrderService` создаётся дважды — сначала с `EmailSender`, потом с `SMSSender`. Код сервиса при этом не меняется, только внедряемая зависимость.

## Тесты

В `main_test.go` `OrderService` тестируется полностью на моках (`MockWriter`, `MockNotifier`), без обращения к реальной БД и без реальной отправки сообщений.

| Тест | Что проверяет |
|---|---|
| `TestOrderService_CreateOrder_Success` | Содержимое сохранённого `Order` (Customer, Products, Total, Status) и текст отправленного сообщения |
| `TestOrderService_CreateOrder_RepositoryError` | При ошибке `SaveOrder` — ошибка возвращается, `Notifier.Send` не вызывается |
| `TestOrderService_CreateOrder_NotifierError` | При ошибке `Send` — заказ уже сохранён, ошибка возвращается вызывающему коду |

Запуск:

```bash
go test ./...
```

## Обработка ошибок

`OrderService` не глотает ошибки, а возвращает их с контекстом. Порядок операций:

1. `SaveOrder` — ошибка оборачивается как `"сохранение заказа: <оригинал>"`, `Send` не вызывается.
2. `Send` — ошибка оборачивается как `"отправка уведомления: <оригинал>"`, заказ в БД остаётся.

Оригинальные ошибки доступны через `errors.Is` — это используется в тестах.

## Запуск

Для сборки требуется CGO (используется `github.com/mattn/go-sqlite3`): нужен C-компилятор (gcc/clang) и `CGO_ENABLED=1` (по умолчанию включён). На macOS — Xcode Command Line Tools, на Ubuntu — `build-essential`, на Windows — MinGW-w64.

```bash
go run main.go
```

Ожидаемый вывод:

```text
[Email] Уведомление отправлено клиенту Иван: Ваш заказ на сумму 10.50 принят в обработку
[SMS] Уведомление отправлено клиенту Мария: Ваш заказ на сумму 5.00 принят в обработку
```

При первом запуске создаётся файл `orders.db` (SQLite).

## Границы решения

- **Products хранится как одна строка.** `fmt.Sprintf("%v", products)` даёт `"[apple banana]"`. В учебном проекте этого достаточно. В продакшене потребовалась бы отдельная таблица `order_products` со связью многие-ко-многим.
- **Нет транзакции между SaveOrder и Send.** Уведомление — внешний побочный эффект, откатить его нельзя. Если `Send` упадёт, заказ остаётся в БД. В продакшене нужен либо retry-механизм, либо outbox-паттерн: сохранять намерение отправить уведомление в БД, а отдельный воркер разбирает очередь.
- **`db.Ping()` после `sql.Open` не вызывается.** Для SQLite `sql.Open` не открывает соединение, ошибка всё равно всплывёт на `repo.Init()`. Явный `Ping` сделал бы диагностику чуть раньше, но в учебном проекте это не критично.
- **Нет тестов на SQLiteRepo.** Он тестируется косвенно через `go run main.go`; в юнит-тестах используется `MockWriter`. Для интеграционного теста понадобился бы in-memory SQLite (`:memory:`) или testcontainers.
- **Нет обработки retry при ошибке уведомления.** Если `Send` упал — ошибка возвращается вызывающему, повторов нет.

Реализовано в рамках курса «Go-разработчик с нуля» (Нетология).
